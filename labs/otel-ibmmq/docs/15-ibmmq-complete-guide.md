# IBM MQ — Complete Guide

A ground-up explanation of IBM MQ: what it is, how it works internally, every
major concept, and how everything connects. Examples are anchored to the lab
stack where relevant.

---

## Part 1 — Mental model

IBM MQ is a **message broker**: a middleman that accepts messages from producers,
stores them reliably, and delivers them to consumers — even when producer and
consumer are not running at the same time.

The fundamental guarantee is **store-and-forward with persistence**:

```
Producer                  IBM MQ                   Consumer
   │                        │                          │
   │── put message ────────>│ written to disk          │
   │                        │ (producer can now exit)  │
   │                        │                          │
   │                        │<────── get message ──────│
   │                        │ deleted from disk        │
```

This is different from:
- **HTTP**: synchronous, both parties must be up simultaneously
- **Kafka**: log-based, messages are retained after consumption and replayed
- **Redis pub/sub**: in-memory only, no persistence, messages lost if consumer is down

IBM MQ's niche is **reliable, ordered, transactional message delivery** for
enterprise systems where losing a message is not acceptable. It has been
production-tested since 1993 (originally called MQSeries).

## Part 2 — Core objects

### Queue Manager (QM)

The Queue Manager is the **central server process**. Everything else — queues,
channels, connections — lives inside a Queue Manager.

```
┌─────────────────────────────────────────┐
│  Queue Manager (QM1)                    │
│                                         │
│  ┌──────────┐  ┌──────────┐            │
│  │ Queue A  │  │ Queue B  │  …         │
│  └──────────┘  └──────────┘            │
│                                         │
│  ┌──────────────────────────────────┐  │
│  │ Channels (network connections)   │  │
│  └──────────────────────────────────┘  │
│                                         │
│  ┌────────┐  ┌──────────┐             │
│  │ Topics │  │ Auth/TLS │  …          │
│  └────────┘  └──────────┘             │
└─────────────────────────────────────────┘
```

A single server can run multiple Queue Managers. Each is an independent unit:
separate config, separate queues, separate channels. You address a Queue Manager
by name, e.g. `QM1`.

Key facts:
- A QM is a Unix process (or set of processes): `amqzmuc0`, `amqzxma0`, `amqrmppa`, etc.
- It has its own filesystem: page sets for queue storage, log files for recovery
- Starting: `strmqm QM1` / Stopping: `endmqm QM1`

---

### Queue

A queue is an ordered list of messages stored by the Queue Manager. Producers
**put** messages onto a queue; consumers **get** messages off a queue.

```
Queue: DEV.QUEUE.1
┌────┬────┬────┬────┐
│ m1 │ m2 │ m3 │ m4 │  ← newest
└────┴────┴────┴────┘
  ↑
 oldest (gets consumed first — FIFO by default)
```

**Queue types:**

| Type | Purpose |
|------|---------|
| **Local** | Physical queue — messages stored here |
| **Remote** | Pointer to a queue on another QM; puts are forwarded via channel |
| **Alias** | Alternative name for a local queue or topic |
| **Model** | Template for creating temporary dynamic queues |
| **Cluster** | Local queue exposed to a QM cluster |
| **Dead Letter (DLQ)** | Receives messages that cannot be delivered |

**Key local queue properties:**

| Property | What it controls |
|----------|-----------------|
| `MAXDEPTH` | Max messages the queue holds (default 5000) |
| `MAXMSGL` | Max message length in bytes |
| `MSGDLVSQ` | Delivery sequence: `FIFO` or `PRIORITY` |
| `PROPCTL` | Whether MQRFH2 message properties flow through (`ALL`, `FORCE`, `COMPAT`) |
| `USAGE` | `NORMAL` (application queue) or `XMITQ` (transmission queue for remote puts) |
| `HARDENBO` | Whether backout count persists across restarts |

**Admin commands:**

```
DEFINE QLOCAL(MY.QUEUE) MAXDEPTH(50000) PROPCTL(ALL)
DISPLAY QLOCAL(MY.QUEUE) ALL
ALTER QLOCAL(MY.QUEUE) MAXDEPTH(100000)
DELETE QLOCAL(MY.QUEUE)
```

### Message

A message is the unit of data transferred. It has two parts:

```
┌─────────────────────────────────────────┐
│  MQMD (Message Descriptor)              │  fixed 364-byte header
│    MsgId, CorrelId, Format, Expiry,     │
│    Priority, Persistence, MsgType, …    │
├─────────────────────────────────────────┤
│  (optional) Extension headers           │  MQRFH2, MQCIH, MQDLH, …
├─────────────────────────────────────────┤
│  Message body                           │  your payload (text, binary, JSON, …)
└─────────────────────────────────────────┘
```

**MQMD key fields:**

| Field | Values / notes |
|-------|---------------|
| `MsgId` | 24-byte unique ID generated by QM at put time |
| `CorrelId` | 24-byte app-defined correlation; used for request-reply matching |
| `Format` | `MQFMT_RF_HEADER_2` ("MQHRF2  "), `MQFMT_STRING` ("MQSTR   "), `MQFMT_NONE` |
| `Persistence` | `MQPER_PERSISTENT` (survives QM restart) or `MQPER_NOT_PERSISTENT` |
| `Priority` | 0–9; higher = consumed first when `MSGDLVSQ(PRIORITY)` |
| `Expiry` | Tenths of a second until the message is auto-deleted |
| `MsgType` | `MQMT_DATAGRAM`, `MQMT_REQUEST`, `MQMT_REPLY`, `MQMT_REPORT` |
| `ReplyToQ` / `ReplyToQMgr` | Where to send a reply (request-reply pattern) |

**MQRFH2 (Rules and Formatting Header v2)**

When `Format = MQHRF2`, the body starts with an MQRFH2 header:

```
Bytes 0-3:   StrucId   = "RFH "
Bytes 4-7:   Version   = 2
Bytes 8-11:  StrucLength (total header length including all folders)
Bytes 12-15: Encoding
Bytes 16-19: CodedCharSetId
Bytes 20-27: Format    (format of the data that follows the header)
Bytes 28-31: Flags
Bytes 32-35: NameValueCCSID
Bytes 36+:   NameValue data (series of length-prefixed XML folder strings)
```

Each folder is `<length><XML>`:
```
00 00 00 2C <usr><traceparent>00-abc…</traceparent></usr>
```

JMS properties map to the `<usr>` folder. `<jms>`, `<mcd>`, `<psc>` are
IBM-defined folders for JMS system properties, message content descriptor,
and publish/subscribe control respectively.

### Channel

A channel is a **communication link** between two Queue Managers, or between a
client application and a Queue Manager. It is the network transport layer.

**Channel types:**

| Type | Direction | Purpose |
|------|-----------|---------|
| `SVRCONN` | Inbound | Client applications connect to QM over this |
| `SENDER` | Outbound | QM pushes messages to a remote QM |
| `RECEIVER` | Inbound | QM accepts messages from a remote SENDER |
| `REQUESTER` | Outbound | QM requests messages from a remote SVRCONN |
| `CLNTCONN` | Client-side | Configured on client to find the QM |
| `CLUSRCVR` | Cluster inbound | Receives messages in a QM cluster |
| `CLUSSDR` | Cluster outbound | Sends messages in a QM cluster |
| `AMQP` | Both | AMQP 1.0 protocol channel |
| `MQTT` | Both | MQTT protocol channel |

**Key channel properties:**

| Property | What it controls |
|----------|-----------------|
| `TRPTYPE` | Transport: `TCP`, `LU62`, `NETBIOS` |
| `CONNAME` | IP/hostname and port of remote end |
| `XMITQ` | Transmission queue this channel drains (SENDER/CLUSSDR) |
| `SSLCIPH` | TLS cipher spec (enables encrypted connection) |
| `CONVERT` | `YES` = convert message format on receipt; can strip MQRFH2 |
| `PROPCTL` | Same as queue: controls property/MQRFH2 flow across the channel |

**Admin commands:**

```
DEFINE CHANNEL(MY.APP.CHANNEL) CHLTYPE(SVRCONN) TRPTYPE(TCP)
DISPLAY CHANNEL(DEV.APP.SVRCONN) ALL
START CHANNEL(MY.SENDER)
PING CHANNEL(MY.SENDER)
```

---

### Connection

An application connects to a QM in one of two modes:

**Bindings mode** (same machine): direct shared-memory connection, no TCP
involved. Used by services running on the same host as the QM.

```
Application process ──shared memory──> Queue Manager process
```

**Client mode**: TCP connection from any machine to a SVRCONN channel.

```
Application ──TCP──> SVRCONN channel ──> Queue Manager
             port 1414 (default)
```

Connection parameters:
- `QMNAME`: target Queue Manager name
- `HOSTNAME` + `PORT`: for client mode
- `CHANNEL`: SVRCONN channel name
- `USER` + `PASSWORD`: for authenticated connections
- `SSL_CIPHER_SPEC`: for TLS

## Part 3 — Messaging models

### Point-to-Point (Queue)

One producer, one consumer. Message is consumed **once** and removed.

```
Producer ──put──> [Queue] ──get──> Consumer
```

Use when: work distribution, command processing, reliable one-shot delivery.

### Publish/Subscribe (Topic)

One publisher, many subscribers. Each subscriber gets its own copy.

```
Publisher ──publish──> [Topic]
                          ├──> Subscriber A (own copy)
                          ├──> Subscriber B (own copy)
                          └──> Subscriber C (own copy)
```

IBM MQ pub/sub uses a **topic tree** with wildcards:
```
orders/+/created    matches orders/acme/created, orders/globex/created
orders/#            matches anything under orders/
```

Subscriptions can be **durable** (persist when subscriber is offline, messages
queued) or **non-durable** (messages only delivered while subscriber is connected).

**Managed vs unmanaged queues**: IBM MQ can auto-create a managed queue per
subscriber (managed subscription) or deliver to a queue you specify (unmanaged).

## Part 4 — APIs

### MQI (Message Queue Interface)

The native C API. Every other API is a wrapper around it. Core verbs:

| Verb | What it does |
|------|-------------|
| `MQCONN` / `MQCONNX` | Connect to a Queue Manager |
| `MQOPEN` | Open a queue or topic for put/get/browse |
| `MQPUT` | Put a message onto a queue |
| `MQPUT1` | Open + put + close in one call (convenience) |
| `MQGET` | Get a message from a queue |
| `MQCLOSE` | Close the queue handle |
| `MQDISC` | Disconnect from the Queue Manager |
| `MQBEGIN` | Begin a global transaction (XA) |
| `MQCMIT` | Commit a unit of work |
| `MQBACK` | Roll back a unit of work |
| `MQINQ` | Inquire queue/channel attributes |
| `MQSET` | Set queue attributes |
| `MQSETMP` | Set a message property |
| `MQINQMP` | Get a message property |

Language bindings: C, C++, Go (`mq-golang`), Python (`pymqi`), Node.js (`ibmmq`),
COBOL. All call the underlying C library.

**MQGMO and MQPMO** are option structures passed to `MQGET` and `MQPUT`:

```c
MQGMO gmo = {MQGMO_DEFAULT};
gmo.Options = MQGMO_WAIT | MQGMO_SYNCPOINT | MQGMO_PROPERTIES_IN_HANDLE;
gmo.WaitInterval = 30000; // 30 seconds
MQGET(hConn, hObj, &md, &gmo, bufferLen, buffer, &dataLen, &compCode, &reason);
```

Key `MQGMO` options:

| Option | Effect |
|--------|--------|
| `MQGMO_WAIT` | Block until a message arrives |
| `MQGMO_NOWAIT` | Return immediately if no message |
| `MQGMO_SYNCPOINT` | Get is part of a unit of work (commit/rollback) |
| `MQGMO_NO_SYNCPOINT` | Get is not transactional |
| `MQGMO_BROWSE_FIRST` | Read first message without removing it |
| `MQGMO_BROWSE_NEXT` | Read next message without removing it |
| `MQGMO_PROPERTIES_IN_HANDLE` | Expose MQRFH2 properties via MQINQMP |

---

### JMS (Java Message Service)

Standard Java API (JSR-343). IBM MQ provides a JMS 2.0 implementation via
`com.ibm.mq.allclient` JAR.

**JMS object hierarchy:**

```
ConnectionFactory
    └── Connection
            └── Session
                    ├── MessageProducer ──> Queue / Topic
                    └── MessageConsumer <── Queue / Topic
```

**Message types**: `TextMessage`, `BytesMessage`, `MapMessage`, `ObjectMessage`,
`StreamMessage`.

**Delivery modes**: `DeliveryMode.PERSISTENT` (written to disk) or
`DeliveryMode.NON_PERSISTENT` (memory only).

**Acknowledgement modes** (non-transacted sessions):
- `AUTO_ACKNOWLEDGE`: auto-acked when `receive()` returns
- `CLIENT_ACKNOWLEDGE`: app calls `message.acknowledge()` explicitly
- `DUPS_OK_ACKNOWLEDGE`: lazy ack; duplicates possible

**Transacted sessions**: `session = connection.createSession(true, 0)`.
Messages are buffered until `session.commit()` or `session.rollback()`.

JMS properties map to MQRFH2 `<usr>` folder automatically. Property names
cannot contain hyphens — use underscores instead (IBM MQ JMS implementation
rejects names with `-`).

---

### IBM MQ REST API

HTTP/JSON API for application messaging. No MQ client library needed.

```bash
# Put a message
curl -X POST \
  https://localhost:9443/ibmmq/rest/v2/messaging/qmgr/QM1/queue/DEV.QUEUE.1/message \
  -H "Content-Type: text/plain" \
  -H "ibm-mq-rest-csrf-token: " \
  -u admin:passw0rd \
  -d "hello world"

# Get a message (destructive)
curl -X DELETE \
  https://localhost:9443/ibmmq/rest/v2/messaging/qmgr/QM1/queue/DEV.QUEUE.1/message \
  -H "ibm-mq-rest-csrf-token: " \
  -u admin:passw0rd
```

Limitations: no transactions, no browsing, no subscriptions, context propagation
is HTTP-header-only (not embedded in the message body). Best for lightweight
use cases or systems that cannot use a native MQ client.

---

### AMQP 1.0

IBM MQ exposes an AMQP 1.0 channel. AMQP `application-properties` map to MQRFH2
`<usr>` folder. Any AMQP 1.0 client (Apache Qpid, Azure Service Bus SDK, etc.)
can connect.

### MQTT

IBM MQ exposes an MQTT channel (MQ Telemetry feature). Used for IoT devices.
MQTT 5 User Properties map to MQRFH2. MQTT 3.1.1 has no property mechanism.

### XMS (.NET and C++)

IBM's proprietary API that mirrors JMS for .NET and C++. API is nearly
identical to JMS; `IMessage.SetStringProperty` maps to MQRFH2 `<usr>`.

## Part 5 — Delivery guarantees

### Persistence

**Persistent** (`MQPER_PERSISTENT`): message written to disk before `MQPUT`
returns. Survives QM restart. Slower (disk I/O on each put).

**Non-persistent** (`MQPER_NOT_PERSISTENT`): message held in memory. Lost on
QM restart or crash. Faster.

Queue default persistence is set with `DEFPSIST(YES/NO)` on the queue
definition.

### At-least-once delivery

IBM MQ guarantees **at-least-once**: a committed message will be delivered to
a consumer at least once. Under failure scenarios (crash after delivery, before
consumer commits), the message is redelivered. Applications must handle
duplicate detection if needed.

The **backout count** (`MQMD.BackoutCount`) tracks how many times a message has
been redelivered after rollback. When it exceeds `BOQNAME` / `BOTHRESH` on the
queue definition, IBM MQ automatically moves the message to the Backout Queue
or DLQ.

### Exactly-once delivery

Achievable with XA distributed transactions coordinating the MQ unit of work
with a database transaction. If both commit or both roll back atomically, you
get exactly-once semantics end-to-end. Requires XA-capable resource managers on
both sides.

### Message ordering

Within a single queue: **FIFO guaranteed** (default). Priority ordering
(`MSGDLVSQ(PRIORITY)`) breaks strict FIFO.

Across multiple queues or QMs: no ordering guarantee without application-level
sequencing.

**Message groups**: related messages can be grouped (`MQMF_MSG_IN_GROUP`,
`MQMF_LAST_MSG_IN_GROUP` in MQMD). A consumer can get an entire group as a
unit.

**Message segments**: a single logical message split across multiple physical
messages (`MQMF_SEGMENT`, `MQMF_LAST_SEGMENT`). IBM MQ can reassemble segments
transparently.

## Part 6 — Transactions

### Local (single QM) unit of work

```
MQBEGIN  (or session.createSession(true, …) in JMS)
  MQPUT  (message goes to uncommitted area)
  MQGET  (message removed from uncommitted area of source queue)
MQCMIT   → both become permanent simultaneously
```

If the application crashes between `MQPUT` and `MQCMIT`, the QM rolls back
automatically on reconnect — the put message disappears, the gotten message
is returned to its queue.

### XA distributed transactions

Coordinates IBM MQ with another XA resource (e.g. a relational database) using
a two-phase commit coordinator (IBM WebSphere, JBoss, Atomikos, etc.):

```
Phase 1 (Prepare):
  Coordinator ──> MQ:  "can you commit?"  ──> MQ writes prepare record to log
  Coordinator ──> DB:  "can you commit?"  ──> DB writes prepare record to log

Phase 2 (Commit):
  Coordinator ──> MQ:  "commit"           ──> message becomes permanent
  Coordinator ──> DB:  "commit"           ──> DB row becomes permanent
```

If the coordinator crashes after Phase 1, both MQ and DB have their prepare
records and will commit on coordinator restart (in-doubt resolution).

XA is the only way to atomically consume from MQ and write to a DB without
duplicate processing.

## Part 7 — High availability

### Multi-Instance Queue Manager (MQHA)

Two QM instances share a network filesystem (NFS, GPFS). Only one runs at a
time (active); the other is standby. On active failure, standby takes over and
resumes from the shared filesystem.

```
Active QM ──reads/writes──> Shared filesystem <──standby–– Standby QM
```

Clients reconnect automatically using the `CCDT` (Client Channel Definition
Table) which lists both hostnames.

Limitation: recovery time depends on NFS failover speed; shared filesystem is
a SPOF.

### Replicated Data Queue Manager (RDQM)

Three QM instances on separate servers. Data is replicated synchronously using
Pacemaker + DRBD (Linux only). No shared filesystem.

```
Server 1 (Active QM)  ──sync replication──>  Server 2 (Standby)
                       ──sync replication──>  Server 3 (Standby)
```

Automatic failover in seconds. The active QM holds a lock; on failure, Pacemaker
elects a new active from the two standbys that have the most recent data.

### IBM MQ Clustering

Multiple QMs connected in a cluster. A queue defined as a cluster queue is
accessible from any QM in the cluster — IBM MQ routes puts to whichever QM
holds the queue.

```
        ┌──── QM1 (cluster)
Client ─┤──── QM2 (cluster)  ← IBM MQ load-balances puts
        └──── QM3 (cluster)
```

Two Repository QMs (full repositories) maintain the cluster topology. All other
QMs hold partial repositories.

Use cases: load balancing, geographic distribution, high availability.

### IBM MQ on Cloud / Containers

**IBM MQ as a Service (IBM Cloud)**: fully managed, no QM administration.
**IBM MQ on OpenShift**: operator-based deployment with `QueueManager` CRD.

```yaml
apiVersion: mq.ibm.com/v1beta1
kind: QueueManager
metadata:
  name: qm1
spec:
  license:
    accept: true
    license: L-RJON-CJR2RX
    use: NonProduction
  queueManager:
    storage:
      queueManager:
        type: persistent-claim
    name: QM1
```

The operator handles multi-instance HA, TLS certificate rotation, and metrics
scraping automatically.

## Part 8 — Security

### Authentication

**No authentication** (development only): `CONNAUTH` set to blank.

**User ID + password**: `CONNAUTH(USE.PASSWORD)`. Credentials checked against
the OS (PAM) or an LDAP directory.

**TLS mutual authentication (mTLS)**: client presents a certificate; QM
validates it against its trust store. Common for service-to-service connections.

**Token-based (JWT)**: IBM MQ 9.3+ supports OIDC token validation via
a custom JAAS authentication plugin.

### Authorization (OAM — Object Authority Manager)

OAM is the default authorization plugin. Permissions are granted on MQ objects:

```
# Allow user 'app' to put/get on queue DEV.QUEUE.1
setmqaut -m QM1 -t queue -n DEV.QUEUE.1 -p app +put +get +browse +inq

# Allow user 'app' to connect to the QM
setmqaut -m QM1 -t qmgr -p app +connect +inq
```

TLS-authenticated clients can map certificate DN to an MQ user ID
(`SSLPEER` on the channel definition).

### TLS

```
DEFINE CHANNEL(SECURE.CHANNEL) CHLTYPE(SVRCONN) +
       TRPTYPE(TCP) +
       SSLCIPH(TLS_AES_256_GCM_SHA384) +
       SSLCAUTH(OPTIONAL)   ← REQUIRED for mTLS
```

Certificates stored in a CMS keystore (`runmqckm` or IBM Key Management tool).

## Part 9 — Dead Letter Queue (DLQ)

When IBM MQ cannot deliver a message (queue full, queue not found, message too
large, exceeded expiry, max retries), it moves it to the DLQ.

IBM MQ prepends an `MQDLH` (Dead Letter Header) before the original message:

```
┌────────────────────────────────────────┐
│  MQDLH (172 bytes)                     │
│    Reason, DestQName, DestQMgrName,    │
│    PutDate, PutTime, …                 │
├────────────────────────────────────────┤
│  Original MQMD                         │
├────────────────────────────────────────┤
│  Original MQRFH2 (if present)          │
├────────────────────────────────────────┤
│  Original message body                 │
└────────────────────────────────────────┘
```

The DLQ handler must strip the `MQDLH`, inspect the reason code, and decide
whether to retry, reroute, or discard. IBM provides a sample DLQ handler
(`runmqdlq`) but production systems typically implement their own.

**DLQ handler checklist for OTel**: extract `traceparent`/`baggage` from the
**original** MQRFH2 (not from `MQDLH`); start a child span tagged as error;
add `MQDLH.Reason` as a span attribute.

## Part 10 — Administration

### runmqsc

The primary admin shell. All configuration changes go through here.

```bash
runmqsc QM1
# now in interactive mode:
DISPLAY QMGR ALL
DISPLAY QLOCAL(*) CURDEPTH
DISPLAY CHANNEL(*) STATUS
DISPLAY CONN(*) TYPE(CONN)
```

Can also run non-interactively:
```bash
echo "DISPLAY QLOCAL(*) CURDEPTH" | runmqsc QM1
```

Or from a script file:
```bash
runmqsc QM1 < config.mqsc
```

### Key admin commands

```
# Queue
DEFINE QLOCAL(MY.Q) MAXDEPTH(50000) PROPCTL(ALL)
ALTER QLOCAL(MY.Q) MAXDEPTH(100000)
CLEAR QLOCAL(MY.Q)           ← destroys all messages
DELETE QLOCAL(MY.Q)

# Channel
START CHANNEL(MY.SENDER)
STOP CHANNEL(MY.SENDER)
RESET CHANNEL(MY.SENDER)     ← resets sequence number
RESOLVE CHANNEL(MY.SENDER) ACTION(COMMIT)  ← resolves in-doubt messages

# Connections
DISPLAY CONN(*) ALL
STOP CONN(<connid>)

# Queue Manager
DISPLAY QMGR ALL
ALTER QMGR MAXMSGL(104857600)  ← increase max message size to 100MB

# Messages (diagnostic browsing)
amqsbcg DEV.QUEUE.1 QM1      ← dumps message hex + header decode
amqsput DEV.QUEUE.1 QM1      ← interactive put (type body, Ctrl+D to send)
amqsget DEV.QUEUE.1 QM1      ← destructive get (prints and removes)
amqsbcg DEV.DEAD.LETTER.QUEUE QM1  ← inspect DLQ messages
```

### MQ Console (web UI)

IBM MQ 9.1+ includes a web console at `https://<host>:9443/ibmmq/console`.
Shows queue depths, channel status, connection list. In the lab: `https://localhost:9443`.

### CCDT (Client Channel Definition Table)

A JSON or binary file distributed to client applications to describe how to
connect to a QM or cluster. Clients set `MQCHLLIB`/`MQCHLTAB` to point to it
instead of hardcoding connection parameters.

```json
{
  "channel": [{
    "name": "MY.APP.CHANNEL",
    "clientConnection": {
      "connection": [{"host": "mq1.example.com", "port": 1414},
                     {"host": "mq2.example.com", "port": 1414}],
      "queueManager": "QM1"
    },
    "type": "clientConnection"
  }]
}
```

## Part 11 — Monitoring

### Queue depth

The most-watched metric. `CURDEPTH` = current number of messages on a queue.
When it approaches `MAXDEPTH` the QM starts rejecting puts with `MQRC_Q_FULL`.

```bash
echo "DISPLAY QLOCAL(*) CURDEPTH" | runmqsc QM1
```

### Statistics and accounting

IBM MQ writes statistics messages to system queues at configurable intervals:
- `SYSTEM.ADMIN.STATISTICS.QUEUE` — queue/channel throughput
- `SYSTEM.ADMIN.ACCOUNTING.QUEUE` — per-connection activity

Enable with:
```
ALTER QMGR STATCHL(LOW) STATQ(ON) STATINT(30) ACCTQ(ON) ACCTINT(30)
```

### Event queues

IBM MQ puts event messages onto system queues when notable things happen:

| Queue | Events |
|-------|--------|
| `SYSTEM.ADMIN.QMGR.EVENT` | QM start/stop, authority failures |
| `SYSTEM.ADMIN.PERFM.EVENT` | Queue full, queue depth threshold crossed |
| `SYSTEM.ADMIN.CHANNEL.EVENT` | Channel start/stop, conversion errors |
| `SYSTEM.ADMIN.LOGGER.EVENT` | Log full |

Enable performance events:
```
ALTER QMGR PERFMEV(ENABLED)
ALTER QLOCAL(MY.Q) QDPHIEV(ENABLED) QDEPTHHI(4000) QDEPTHLO(1000)
```

### Prometheus / Grafana

IBM MQ 9.1+ ships a Prometheus metrics exporter (MQ Exporter for Prometheus).
Exposes queue depth, put/get rates, channel status as Prometheus metrics.
The lab's `docker-compose.yml` uses the OTel Collector's `prometheusreceiver`
to scrape and forward these metrics.

Key metrics:
```
ibmmq_queuemanager_current_depth          ← total across all queues
ibmmq_queue_depth_current{queue="..."}    ← per-queue depth
ibmmq_channel_status{channel="..."}       ← 0=stopped, 3=running, 6=retrying
ibmmq_queue_put_rate{queue="..."}         ← puts/second
ibmmq_queue_get_rate{queue="..."}         ← gets/second
```

## Part 12 — IBM MQ Internals

### Page sets and buffer pools

Queue message data is stored in **page sets** — pre-allocated files on disk.
Each page set is divided into 4KB pages. A **buffer pool** is an in-memory
cache for page set pages.

```
Buffer pool (memory)
   ├── pages from page set 0 (system data)
   └── pages from page set 1 (application queues)

Page set 0: /var/mqm/qmgrs/QM1/qm/qm0.log
Page set 1: /var/mqm/qmgrs/QM1/qm/1/qm0001.pmq
```

Hot pages (frequently accessed queues) stay in the buffer pool. Cold pages are
written back to the page set file.

### Logs

IBM MQ uses a **write-ahead log** for recovery. There are two log modes:

**Circular logging** (default, development): fixed-size log files reused in a
ring. Cannot perform media recovery. Sufficient for HA with RDQM/multi-instance.

**Linear logging**: log files kept indefinitely. Required for point-in-time
recovery after media failure. Used in production systems where data loss is
unacceptable.

Log files are in `/var/mqm/log/QM1/`. The active log tells the QM what
transactions are in-flight; on restart, uncommitted transactions are rolled back
using the log.

### The Kernel Threads

When you `strmqm`, IBM MQ starts several processes:

| Process | Role |
|---------|------|
| `amqzxma0` | Execution controller — parent of all MQ processes |
| `amqzmuc0` | Channel initiator — manages channel start/stop |
| `amqrmppa` | Pooled process agent — reused for put/get operations |
| `amqzlaa0` | Logger — writes to log files |
| `amqzfuma` | File system manager |
| `amqpcsea` | Command server — processes admin commands from `runmqsc` |

Each connected application gets a thread in `amqrmppa` (pooled) or its own
agent process (non-pooled), depending on `MAXPROCSPERQ` settings.

## Part 13 — IBM MQ vs Kafka

Common question: when do you use IBM MQ vs Apache Kafka?

| Dimension | IBM MQ | Kafka |
|-----------|--------|-------|
| **Model** | Store-and-forward queue | Distributed log |
| **Retention** | Until consumed (deleted on get) | Time/size-based (independent of consumption) |
| **Ordering** | FIFO per queue, guaranteed | Per-partition, not across partitions |
| **Throughput** | Moderate (millions/day typical) | Very high (millions/second) |
| **Latency** | Low (ms) with non-persistent | Very low (sub-ms at scale) |
| **Transactions** | XA + JMS transactions, ACID | Kafka transactions (idempotent producer) |
| **Protocol** | Proprietary MQI, JMS, AMQP, REST | Kafka binary protocol |
| **Consumer groups** | Competing consumers on a queue | Consumer groups per topic partition |
| **Replay** | No (consumed = gone) | Yes (rewind offset) |
| **Ideal for** | Transactional enterprise messaging, financial systems, guaranteed delivery, legacy integration | Event streaming, analytics, log aggregation, large-volume pipelines |
| **Maturity** | 30+ years, CICS/mainframe integration | 10+ years, cloud-native |

**Rule of thumb**: IBM MQ when you need transactional guarantees and legacy
system integration. Kafka when you need high-throughput event streaming or
replay capability.

## Part 14 — Common operational patterns

### Message selector (filtered consume)

Consume only messages matching a JMS selector (evaluated against message
properties / MQRFH2 `<usr>` entries):

```java
MessageConsumer consumer = session.createConsumer(queue,
    "tenant_id = 'acme' AND priority > 5");
```

IBM MQ evaluates the selector server-side using MQRFH2 properties. Mis-matched
messages are left on the queue (not consumed).

### Poison message handling

A message that consistently causes consumer exceptions will cycle indefinitely.
IBM MQ tracks the backout count in `MQMD.BackoutCount`. Set on the queue:

```
ALTER QLOCAL(MY.Q) BOTHRESH(3) BOQNAME(MY.DLQ)
```

After 3 rollbacks, IBM MQ automatically moves the message to `MY.DLQ`.

### Trigger-based processing

IBM MQ can automatically start an application when a message arrives on a queue:

```
ALTER QLOCAL(MY.Q) TRIGGER TRIGTYPE(FIRST) TRIGDPTH(1) PROCESS(MY.PROCESS)
```

The trigger monitor (`runmqtrm`) watches for trigger events and starts the
process. Useful for batch jobs that should only run when work is available.

### Browsing without consuming

```java
QueueBrowser browser = session.createBrowser(queue);
Enumeration msgs = browser.getEnumeration();
while (msgs.hasMoreElements()) {
    Message msg = (Message) msgs.nextElement();
    // inspect without removing
}
```

Or via MQI: `MQGET` with `MQGMO_BROWSE_FIRST` + `MQGMO_BROWSE_NEXT`.

### Request-reply

```java
// Requester
TemporaryQueue replyTo = session.createTemporaryQueue();
msg.setJMSReplyTo(replyTo);
msg.setJMSCorrelationID(UUID.randomUUID().toString());
producer.send(requestQueue, msg);

// Wait for reply on the temporary queue
Message reply = replyConsumer.receive(5000);

// Responder (separate service)
Message request = consumer.receive();
TextMessage reply = session.createTextMessage("result");
reply.setJMSCorrelationID(request.getJMSCorrelationID());
producer.send(request.getJMSReplyTo(), reply);
```

## Part 15 — Key gotchas

| Gotcha | Explanation |
|--------|------------|
| `PROPCTL(FORCE)` strips MQRFH2 | Default on some queue templates. Check every queue in the path. |
| JMS property names with hyphens | `setStringProperty("trace-parent", …)` throws. Use `traceparent` (underscores or no separator). |
| `MQFMT_STRING` loses properties | If producer sets `MQMD.Format = MQSTR`, there is no MQRFH2. No properties possible without format change. |
| `CONVERT(YES)` on channels | Can strip or corrupt MQRFH2 when converting between code pages. Set `CONVERT(NO)` for property-carrying messages. |
| Non-persistent messages and QM restart | Non-persistent messages are silently lost on QM restart or crash. Never use for critical data. |
| Backout loop | Consumer rolls back → message redelivered → crash → loop. Always set `BOTHRESH` + `BOQNAME` on every application queue. |
| Queue depth alert lag | `MAXDEPTH` defaults to 5000. A fast producer can hit this in seconds. Monitor `CURDEPTH` and alert before 80% full. |
| DLQ full | If the DLQ itself is full, IBM MQ cannot move poison messages and begins rejecting puts on the source queue. Monitor DLQ depth. |
| Temporary queue cleanup | JMS `TemporaryQueue` is deleted when the session closes. If the session crashes before the reply arrives, the reply is lost to the DLQ or `SYSTEM.DEAD.LETTER.QUEUE`. |
| MQ client version mismatch | Client and QM must be within supported version compatibility range. A very old client connecting to a new QM may not support MQRFH2 v2 or TLS ciphers. |
